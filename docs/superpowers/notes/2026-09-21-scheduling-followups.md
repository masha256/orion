# Sub-project 4 (scheduling and delivery): rulings and follow-ups

Carried out of the subagent-driven execution of `docs/superpowers/plans/2026-09-21-orion-scheduling.md` on branch `feat/scheduling` (tasks 1 to 8, a final whole-branch review, one fix wave, and a scoped re-review; 568 tests before, 645 after; engine unchanged at 1.2.0). The working ledger was scratch; this file is the durable record. Task 9 (deploy checkpoints) is the user's and is listed at the end.

## How the execution went, in one paragraph

The plan's code was generated from a tested prototype and verified by extraction, so every implementer applied it byte for byte with `apply-step.py` and no task needed a fix for a transcription error. Task reviews found design defects the plan's own tests had pinned as correct in 7 of 8 tasks: an unguarded lock release that could turn a paid, successful run into a `database is locked` failure; a calendar date regex that let `2026-02-30` shift silently to March; a test that claimed to pin the config hash and pinned nothing; a local `DAYS_PER_YEAR = 365.25` shadowing the engine's 365; duplicate calendar dates that made every tick for a week fail on the unique index; a report that denied a completed run when appending `signals.jsonl` threw, and lost the report entirely when `attachRun` threw; the agent's assumption-change rationale (model text) on tick's stderr while the Hermes prompt says to quote stderr verbatim. The final review, on the most capable model and pointed at the real clock and cross-task interactions, then found what no task review could: under the default 7-day cadence a completed weekly reset the deviation anchor and the trigger could never fire; interval boundaries at exactly N days were decided by fetch jitter; standing firings were invisible, so a 60-day staleness with a failed triage produced 60 silent reports; a committed run whose revaluation failed reported clean; the Hermes job's 30-minute timeout could kill a deep run mid-flight.
