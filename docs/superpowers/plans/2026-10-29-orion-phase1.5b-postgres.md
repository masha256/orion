# Orion Phase 1.5b: Postgres, the SQLite importer and the row-for-row proof. Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Orion runs on Postgres 18 through an async `Db` interface over `pg`. A dev-only importer copies a SQLite
`.backup` into an empty schema, and a proof tool shows that the copy is identical row for row and that `report yield`
output is byte-identical to the SQLite release.

**Architecture:** The conversion runs bottom-up on SQLite first, so every intermediate commit has a green suite with no
Postgres installed. Task 1 adds the final async interface (`all/one/run/tx`). A SQLite compat adapter implements it,
and during the transition the same object still carries the old better-sqlite3 methods. Tasks 2-6 move every caller and
test onto the interface, one module group at a time. Task 7 adds the `pg` implementation, the `0001_baseline.sql`
migration and the test infrastructure, all tested on their own. Task 8 swaps the app and the test helpers to Postgres,
deletes the compat layer and `run_locks`, and adds `orion db migrate|status`. Tasks 9-10 build the importer and the
proof tool, and Task 11 runs both against a `.backup` copy of the live DB.

**Tech Stack:** TypeScript 7 (Node 26, ESM), `pg` (node-postgres) 8.x, PostgreSQL 18 (PGDG), vitest 5, commander,
better-sqlite3 13 (dev-only from Task 8: importer, proof, fixtures).

**Spec:** `docs/superpowers/specs/2026-10-28-orion-platform-postgres-design.md` (rev 3): Status, §1, §3.3, §7, §8.1-8.2,
§13 (D7, D8, D9, D12). The spec's §1 and §7.1 figures were measured before Phase 1 merged; this plan's "Measured scope"
and "Spec corrections" sections supersede them.

## Global Constraints

- PostgreSQL **18** (D12), local socket `/var/run/postgresql`, peer auth; no ORM or query builder; SQL stays hand-written with `$n` placeholders.
- Type parsers, set per pool (never on the global `pg.types`): int8 → `Number`, throwing above 2^53; timestamptz →
  `<pg's own Date parser>(v).toISOString()`, i.e. the same 24-char ISO string as today (D7); date → raw `YYYY-MM-DD`;
  json → raw text (callers already `JSON.parse`). float8 keeps pg's default `parseFloat`.
- Column types (§7.1): ids `bigint GENERATED BY DEFAULT AS IDENTITY`; REAL → `double precision`; text → `text COLLATE "C"`;
  `*_json` → `json` (never `jsonb`); `dry_run` → `smallint CHECK (dry_run IN (0,1))`; block numbers and counters → `bigint`.
- Migrations run only through `orion db migrate`, never on open. On open, a schema behind the code is refused; a schema
  ahead is allowed. Migrations are expand-only, and a `-- breaking` first line requires `--breaking` (§3.3).
- Every transaction that reads before it writes goes through `db.tx(fn, { lockAsset })`. Inside `tx`, only the tx
  handle is used, and there is no network I/O.
- Tests: a real local Postgres (D9); `ORION_TEST_DATABASE_URL` unset fails the suite with a message (no skip); one fresh
  schema `t_<hex>` per test file; pool `max: 1` in tests; no DB mocks.
- **No reported number changes:** `report yield <a> --day <D> --json` is byte-identical between the SQLite release
  (branch base `dcc2c48`) and this branch on the same imported data, for all 13 assets (aero, cake, crv, cvxcrv,
  hype, link, lit, pump, sdcrv, sky, uni, vvv, ycrv).
- No `assets/*.yaml`, persona or skill edits; no config hash moves. Any task that moves a pinned hash: stop and report.
- History carried (D8, with this plan's corrections): kept tables in full except observations of metrics not declared
  in the release's YAML (Phase 1 D3a), `assumption_value` proposals, and transcripts of non-disclosure runs.
- Test commands: `npx vitest run --maxWorkers=2`, then `npm run typecheck`. From Task 7 on, prefix
  `ORION_TEST_DATABASE_URL='postgresql://orion_dev@/orion_test?host=/var/run/postgresql'`. CLI test files that time out are rerun
  alone with `--maxWorkers=1`; report both runs' real counts.

## Review Focus

1. **SQLite values Postgres cannot hold as-is**: a timestamp that is not a canonical 24-char ISO instant (no
   milliseconds, an offset, a bare date), or a text value containing a NUL byte. The importer must refuse and name
   the table, id and column; it must never rewrite the value silently. Pinned in Task 9 (`import: refuses a
   non-canonical timestamp`, `import: refuses a NUL byte`).
2. **A carried row pointing at an excluded one**: a pending `confirm_observation`/`reject_observation` proposal
   whose observation is an undeclared metric, or a `superseded_by` chain across the exclusion line. The importer
   must refuse and list the ids, not import a proposal that would fail on approve. Pinned in Task 9 (`import: refuses
   a dangling reference`).
3. **Imported historical agent runs without a transcript** (weekly/triage/deep/bootstrap, 48 of 49 live): `agent runs
   list` and `agent runs show <id> --json` must exit 0 and show the transcript as null. Pinned in Task 9 (`import:
   a carried weekly run without transcript still shows`).
4. **A killed or concurrent run on one asset**: a second `tick`/`agent run` must get `run_in_progress` naming the holder
   and since when. Once the holder's process is gone, the next acquire must succeed at once and mark that asset's
   orphaned `running` agent runs `error/abandoned`. Pinned in Task 8 (`lock: ...` cases).
5. **Code that passes `db` instead of the `tx` handle inside a transaction** must fail fast with `db_pool_timeout`,
   never hang or run outside the transaction. Pinned on SQLite in Task 1 and on Postgres in Task 7 (`guard: ...`).

## Spec corrections (post-Phase-1 code vs the spec)

1. **`journal` is live**, not "not carried" (§7.1, D8): disclosure runs write it (`Ledger.commit` →
   `insertJournalEntry`), and the context pack and `get_journal` read it. It goes in the baseline and is carried in full.
2. **`config_versions` has no reader or writer** after Phase 1; the spec lists it as carried. This is decision P1.
3. **`run_locks` is still live**: `withRunLock` serves `tick` and `agent run`, and a takeover abandons orphaned agent
   runs. The spec treats it as gone. Task 8 replaces it with the session advisory lock, keeps the abandonment rule and
   the holder name (the tick report's `lock.holder`), and drops the table.
4. **Undeclared metrics are not carried** (Phase 1 D3a: 2,481 `revenue_run_rate_usd` rows on 12 assets, plus any
   dominance rows left undeleted). The carried observation count is therefore below SQLite's. The sequence still
   continues at `sqlite_sequence` (27,447 in §1), and the excluded ids go in the manifest.
5. **`documents.published_at` stays `text`.** It holds a date *or* an instant with a zone, stored as given;
   `timestamptz` would rewrite `2026-10-22T16:00:00Z` as `…00.000Z` and turn a date into a midnight instant.
6. **`observations.superseded_by` points forward** (a new row supersedes older ids), so "copy in FK order" cannot
   satisfy it. The FK is `DEFERRABLE INITIALLY IMMEDIATE`, and the importer runs `SET CONSTRAINTS ALL DEFERRED`.
7. **One advisory key for both locks would deadlock.** §7.3 keys the session lock (whole refresh) and the
   transaction lock (each write) on the same `sha256('orion:asset:'+id)`. A refresh holding the session lock on one
   connection would then block its own writes on its pool connection. With a CLI pool of 1, holding the session lock
   on the pool's only connection would starve everything else. This plan uses two key spaces (`orion:run:` for the
   session lock, `orion:asset:` for the transaction lock) and holds the session lock on a dedicated non-pool connection.
8. **No CLI test spawns a subprocess** (§1, §7.5): every CLI test runs `buildProgram` in-process. The database therefore
   reaches them through `CliContext.database`, not the environment.
9. **Dialect inventory** (§1): the counts in the table above replace the spec's. The `EXISTS` boolean in
   `listDocuments` was missed, and `INSERT OR IGNORE` no longer exists.
10. **Importer seeding `asset_registry`** (§8.1) moves to 1.5c with the table (migration `0002`).
11. **`.sql` migrations are not emitted by `tsc`**: `npm run build` must copy `src/db/pg/migrations/` into `dist/`.
12. **Phase 1's stored-`assumption_value` tests** (its Review Focus 2) cannot insert such a row under the new CHECK.
    They become "the database refuses it", and the inbox case moves to a stored `config` proposal with an old effect.

### Task 1: The async `Db` interface and the SQLite compat adapter

**Files:**
- Modify: `src/db/connection.ts`
- Create: `src/db/sqliteCompat.ts`
- Test: `tests/db/compat.test.ts`

**Interfaces:**
- Produces (`src/db/connection.ts`):

```ts
export type SqlParam = string | number | bigint | null | readonly number[] | readonly string[];
export interface RunResult<R> { rowCount: number; rows: R[] }
export interface TxOptions { lockAsset?: string }
/** The final interface (Task 8 renames it Db). A tx handle is the same type; a nested tx is a SAVEPOINT. */
export interface DbCore {
  all<R = Record<string, unknown>>(sql: string, params?: readonly SqlParam[]): Promise<R[]>;
  one<R = Record<string, unknown>>(sql: string, params?: readonly SqlParam[]): Promise<R | undefined>; // first row or undefined
  run<R = Record<string, unknown>>(sql: string, params?: readonly SqlParam[]): Promise<RunResult<R>>;
  tx<T>(fn: (tx: this) => Promise<T>, opts?: TxOptions): Promise<T>;
}
/** @deprecated transition only: removed in Task 8. */
export type LegacySqlite = Pick<Database.Database, 'prepare' | 'exec' | 'pragma' | 'transaction' | 'inTransaction'>;
export type Db = DbCore & LegacySqlite;                 // Task 8: `export type Db = DbCore`
export type OrionDb = Db & { close(): Promise<void> };
export function openDb(path: string, opts?: { txWaitMs?: number }): OrionDb;   // Task 8 replaces the signature
```

- SQL is written Postgres-style: `$1..$n`; `RETURNING id` instead of `lastInsertRowid`; `rowCount` instead of
  `.changes`. The adapter rewrites `$n` → `?` outside quoted literals, and reorders and repeats params by occurrence.
  `run` on a statement with `stmt.reader` true returns its rows (RETURNING); otherwise `rows: []` and
  `rowCount = changes`.
- `tx`: `BEGIN IMMEDIATE` at depth 0 (today's semantics), `SAVEPOINT sp<n>` when nested. `lockAsset` is accepted and
  ignored on SQLite. Rollback on throw; the error propagates unchanged.
- Guard: while a transaction is open, calls on the root handle (not the tx handle) wait for it to end. After
  `txWaitMs` (default 5000) they reject with `OrionError('db_pool_timeout', 'waited <ms> ms for a connection: inside db.tx, query through the tx handle')`.
  This mirrors the pg pool of 1. Legacy sync calls bypass the guard.

- [ ] **Step 1: Write the failing tests** in `tests/db/compat.test.ts`:
  - `compat: $n placeholders bind by number, repeat, and skip quoted text` (`SELECT $2 AS b, $1 AS a, $1 AS a2, '$1' AS lit` with `['x','y']` → `{b:'y',a:'x',a2:'x',lit:'$1'}`).
  - `compat: run returns RETURNING rows and rowCount` (insert … RETURNING id → `rows[0].id === 1`, `rowCount === 1`; update of 0 rows → `rowCount 0`).
  - `compat: tx commits, rolls back on throw, nested tx is a savepoint` (inner throws and is caught → outer's rows stay; outer throws → nothing).
  - `compat: legacy prepare inside an async tx joins it` (row written via `t.prepare` is gone after rollback).
  - `guard: a root-handle query inside tx rejects db_pool_timeout` (`txWaitMs: 100`; `db.tx(async () => db.one('select 1'))` rejects with that code) (Review Focus 5).
  - `guard: a root-handle query from another chain waits and then runs` (resolves after the tx commits, sees its row).
